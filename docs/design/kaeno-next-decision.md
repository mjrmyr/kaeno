# Kaeno redesign — synthesis record

**Status:** target architecture; the first local service + sandboxed worker slice is implemented in `src/` (see `README.md`). Remote identity, supervisor, and multi-host placement are not yet implemented. Presentation: [visual overview](kaeno-next.html) · [standalone drawing](kaeno-next.svg).

## Ground and usage

Current `src/tui.ts` opens `src/contact.ts`'s local, loopback-gated Pi Durable Harness and SQLite store. `src/jobs.ts` creates same-process native tasks/child conversations, with a read/list path guard. These are good local primitives, not a remote service or OS sandbox. Native Pi durability holds within one Harness/store; distributed ownership, event transport and external effects need a separate protocol. The previous remote-host arena was withdrawn under the *old local-only contract*, not disproven for these new requirements. A caller should connect from any device, address a stable team conversation, choose a reviewed specialist and per-assignment grant, steer by assignment ID, then resume watching from a cursor; it should not know Pi task IDs, host IDs or storage formats.

## Arena and red-flag review

Two independently generated designs were read in full. Candidate A (`/tmp/kaeno-redesign/candidate-a/design.md`) uses a versioned team/job API and scoped capability ceilings. Candidate B (`/tmp/kaeno-redesign/candidate-b/design.md`) uses assignment cells and a durable supervisor inbox. A readonly cross-judge (`/tmp/kaeno-redesign/judge.md`) scored A 24/30 and B 22/30 against identity, isolation, Pi ownership, supervision, API and feasibility; parent concurs. Original second runner timed out; alternate runner produced B. Only one available model family was used; this is not cross-family corroboration.

**Base A; graft B's supervisor inbox/outbox, deduped review timers and ledger-enforced budgets.** Keep one control ledger and one command path, not B's parallel Thread/Assignment authority. Rejected the single shared Harness (cannot isolate a job), peer-to-peer agents (split ownership/discovery), and stateless transcript-reconstruction (not Pi Durable continuity). Public clients interact with one deep team/assignment API; the ledger owns command receipts and leases, each sandbox owns only its Pi store. No pass-through scheduling façade, shared writers or hand-synced agent lists. Agent revisions are immutable, while per-job grants narrow their authorized ceiling. The supervisor is another agent with scoped tools, never the owner of worker stores.

## Invariants and design gates

- Assignment acceptance: `(principal, requestId)` dedupes acceptance; immutable pinned agent/skills/knowledge/workspace source and effective grant. Skills with code require review and digest pinning. Data knowledge is untrusted content, not a tool grant. Publisher cannot grant itself new privileges.
- Running job: one host/epoch owns a sandbox + Pi store + workspace. The host must meet secret trust/pool policy, not merely advertise resources. All clients are projections of persisted events, not Harness owners.
- Inbox → Pi boundary: persist command before delivery, submit with stable Pi request ID, record its receipt; reattempt on recovery until receipt. Pi and Postgres are not one transaction. Replay can repeat provider calls; external effects require gateway idempotency or human approval.
- Pi → control boundary: local outbox from committed Pi progress, replay to ledger keyed by `(assignment, epoch, sourceSeq)`; ledger dedupes. Verify these persistence edges with crash injection before claiming correctness.
- Supervisor: one long-lived isolated Pi Harness per team, event/timer-driven inbox; review budget/cooldown enforced on command admission; deterministic cycle IDs. Steering is queued, auditable, and applied at worker turn boundaries; no token-by-token micromanagement or infinite review loop.
- Host loss: lease expiry marks suspect, not permission to duplicate work. Fence old execution and revoke credentials before restoring a sealed store+workspace checkpoint on a trusted destination. If unable, block and escalate. Revision of env/keys pauses old cell and starts a newly authorized epoch; do not silently hot-edit a running process.
- Isolation gate: real OS-enforced workspace/mount, filesystem, process, network and resource restrictions; no arbitrary host path or raw secret from a chat prompt. Even a sandbox cannot prevent an authorized agent from exfiltrating data over allowed egress; secrets should be brokered into tools, not the model context.

## Migration and risk

Replace the existing local contact/TUI owner with a durable service; retain the terminal UI as a client. Export existing SQLite contact/job history as read-only provenance; start new isolated assignments instead of transplanting native child tasks. First slice now runs a token-authenticated loopback API, browser and CLI clients, a SQLite ledger, per-assignment Pi Durable worker and scoped macOS Seatbelt prototype policy. Offline tests cover request deduplication, steering, replayable events, OS denial of sibling home files, and blocked restart of an interrupted worker. This is not a hardened sandbox: macOS paths outside home and live-mode outbound traffic remain broad. Next: build a long-lived Pi Durable supervisor with bounded reviews, then replace the experimental sandbox with a verified container/microVM and add secure remote access and host pools. No production deployment, live OpenAI call, cross-host fencing or automatic migration is claimed. Open choices: acceptable container vs microVM isolation, storage RPO, trusted host enrollment and which external tools require approval.

**Principles used:** Redesign from first principles removed the local Harness as the architectural center; foundational thinking gave each store/assignment one writer; boundary discipline placed credential and grant enforcement at ingress and host creation; make operations idempotent shaped inboxes/receipts; laziness/minimize reader load kept one public API and one ledger; prove it works keeps deployment and crash guarantees as gates rather than claims.
