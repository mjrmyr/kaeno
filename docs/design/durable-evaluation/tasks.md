## Components Found

At the pinned source, Pi Durable is an **experimental** harness; its API may change without notice (`packages/durable/README.md:3`). It supplies a single-Session atomic commit line, durable conversations and submissions, checkpointed tasks, task/conversation ownership, and SQLite storage (`docs/spec.md:65-77`; `src/harness/harness.ts:150-205`). These are real facilities Kaeno can use, not evidence that its application-level completion policy is already implemented.

The relevant APIs are `Harness.open()`, `root()`, `resume()`, `Conversation.submit()`, `Conversation.commit()`, `tx.createTask()`, `tx.createConversation()`, `TaskRuntime.commit()`, `Harness.getTask()`, `waitForTask()`, `inspect()`, `abortTask()`, and `Conversation.abort()` (`docs/spec.md:451-569,1604-1720`). **There is no inspected `onComplete` task hook**: the built-in hooks include `GenerationHooks.onYield` and `afterTools`, not an atomic worker-completion notifier (`src/harness/types.ts:629-645`).

## Flow

1. **Background admission.** Example 23’s `subagent` tool makes one `api.commit()` that creates a background, conversation-owned `Anchor` task, its task-owned child conversation, the name→conversation document mapping, and a background `Reporter` task for the first message (`test/examples/23-subagent-background.ts:201-234`). Background ownership makes parent ordinary abort and idle traversal skip the subtree; direct child operations or `abort({ background: true })` can reach it (`docs/spec.md:1937-1961,2089-2110`; `src/harness/scheduler.ts:315-341,676-744`). An anchor that decides `completed` is held as `completing` while its child has ordinary live work, then becomes terminal; later work in that persistent conversation remains possible (`docs/spec.md:2111-2146,3039-3049`).

2. **Execution and reporting are later commits.** The reporter separately submits child input with `requestId: "subagent:<reporter task ID>"`, waits for settlement, commits its `report` checkpoint and `reported` answer marker, then separately submits a parent `followUp` input with `requestId: "subagent-report:<reporter task ID>"`, and finally commits its own terminal outcome (`test/examples/23-subagent-background.ts:83-133`). `Conversation.submit()` durably admits and deduplicates a request ID *within that conversation*; it does not compare content for an existing ID (`src/harness/submissions.ts:129-151`; `test/harness-submissions.test.ts:82-106`). Parent input may queue while busy; settlement or narration is not implied by admission (`src/harness/submissions.ts:152-193`; `docs/spec.md:2222-2280`).

3. **Tool completion.** Generation atomically appends the tool-calling assistant entry, creates `pi.tool` tasks and slots, and checkpoints itself as waiting; tools can run in parallel or, for a sequential round, one at a time (`src/harness/generation.ts:545-590`). Each tool commits intent before `execute()`; its eventual result entry, slot update, usage when supplied, and task outcome are in its **result commit** (`src/harness/tool.ts:58-98,378-410,463-493`). Generation waits for terminal tool tasks before applying `afterTools` and continuing or ending the run (`src/harness/generation.ts:595-646`). A task’s own `runtime.commit()` can likewise atomically combine its checkpoint/outcome with application documents, entries, and newly created tasks (`src/harness/scheduler.ts:1105-1135`; `docs/spec.md:1722-1740`).

**Atomicity answer:** example 23’s *delegate creation + name mapping + reporter creation* are atomic with one another, **not** with the later built-in tool-result entry. Child message admission, child answer, reporter checkpoint, parent follow-up admission, and reporter terminal outcome are separate commits (`test/examples/23-subagent-background.ts:83-133,201-239`; `src/harness/tool.ts:378-410`). There is no built-in application outbox or `onComplete` that atomically notifies the contact. A custom worker task **could** write its terminal outcome and a Kaeno completion document/task in one `runtime.commit()`; delivering that completion as a parent model input is another operation unless Kaeno implements and verifies that admission path. `tx.createSubmission()` alone is a raw record, explicitly *without* inbox/admission rules (`docs/spec.md:3051-3062`; `src/session/transaction.ts:428-435`).

## Replay, effects, scheduling, and close

- Open reconciles surviving `running` tasks to `pending`, retains their checkpoints, and derives unfinished ownership cascades/finalizations; it dispatches no handlers until `resume()` or a progress-requesting call (`src/harness/scheduler.ts:241-274`; `docs/spec.md:568-601`). Reservation is persisted before handlers run, and `TaskRuntime.commit()` gates writes against the current task, invocation, close, and abort mark (`src/harness/scheduler.ts:752-799,1266-1291`). Missing/incompatible task definitions remain blocked rather than silently completing; aborting one may produce `orphaned`, not proof of cleanup (`src/harness/scheduler.ts:805-883`; `test/harness-tasks-recovery.test.ts:429-600`).
- **Checkpointing does not make external effects exactly once.** The prescribed pattern is commit intent → perform effect → commit outcome; recovery in the intent phase must retry safely, reconcile, or record interruption (`docs/spec.md:1872-1887`). A built-in tool defaults to `replay: "unsafe"`: after committed intent, it returns an `interrupted` error instead of rerunning. Rerun requires *both* the stored and currently resolved declarations to say `safe`; before intent, hooks can run again (`src/harness/tool.ts:58-117`; `test/harness-tools-recovery.test.ts:109-160,213-250`). A replay-safe tool still needs effect-specific idempotency. Interrupted model requests can be resent from their committed request checkpoint (`test/harness-generation-recovery.test.ts:76-133`).
- The scheduler reserves **every eligible task** in a pass and runs handlers off the Session line; the inspected settings provide a per-tool-round `"parallel"`/`"sequential"` choice, **not** Kaeno’s global/per-agent worker caps or queue budget (`src/harness/scheduler.ts:752-799,891-911`; `src/harness/generation.ts:555-590`; `src/harness/types.ts:421-441`). One conversation’s busy input queues as steer/follow-up; this is not a bounded or preferential contact-completion queue (`docs/spec.md:2222-2300`).
- Abort is durable intent and bottom-up cooperative cancellation, not rollback. Normal parent abort excludes background boundaries; `{ background: true }` crosses those reached at admission. Queued inputs are withdrawn, but queued passive writes remain (`src/harness/scheduler.ts:315-341,513-552`; `test/harness-ownership.test.ts:247-264`). `close()` seals admission, signals **all** invocations including background ones, joins them, and writes no terminal task outcome. Code ignoring cancellation can hold close and storage open indefinitely (`src/harness/scheduler.ts:731-745`; `src/session/session.ts:351-367`; `test/harness-lifecycle.test.ts:127-252`).

## Storage and ownership boundary

One Session commit is atomic across its records and documents; SQLite implements it with one SQL transaction (`docs/spec.md:65-77`; `src/storage/sqlite/storage.ts:173-200`). The inspected SQLite test checks rollback of rows and sequence allocation for a rejected batch (`test/sqlite-storage.test.ts:307-340`). This says **nothing** about atomically committing an external effect or two *separate* Session commits. A failed storage commit with uncertain effect poisons the Session rather than allowing continued writes (`src/session/session.ts:411-449`).

**Multiple harnesses must not own the same storage concurrently.** The README expressly says one process owns storage and there is *no cross-process locking* (`README.md:536-545`). Node SQLite has a connection-local operation queue and `BEGIN IMMEDIATE`, not a Kaeno/Harness lifetime lease (`src/storage/sqlite/node.ts:25-62,139-157`). `SqliteStorage` also holds an in-memory `nextId` initialized on open (`src/storage/sqlite/storage.ts:143-175,204-210`). The test establishes reopening **after** close, not simultaneous owners (`test/harness-lifecycle.test.ts:197-228`). Kaeno’s proposed process-lifetime single-owner guard remains necessary; SQLite transaction locks are not a substitute.

For power/host-failure guarantees, Node SQLite uses WAL with `synchronous = NORMAL`; the README warns the newest commit can be lost on power or host failure (`src/storage/sqlite/node.ts:184-194`; `README.md:536-545`). Do not turn process-crash recovery tests into a stronger durability claim.

## Boundaries for Kaeno

Because `minimal-kaeno.md` explicitly describes **proposed, not implemented**, modules, these are design deletions rather than deletions of existing code:

- **Remove the proposed parallel durability ledger** in `store.ts` for transcript, task records/attempt checkpoints, ordinary user intake, and application documents when one Durable Session/storage is the chosen authority. Use `submit({requestId})`, task receipts, and committed docs instead (`docs/spec.md:568-612,1722-1740`; `src/harness/submissions.ts:129-193`).
- **Shrink, do not eliminate `tasks.ts`.** Durable owns task reservation, recovery, ownership traversal, waiting, and abort mechanics. Kaeno still owns task IDs exposed to users, agent-definition snapshots/version compatibility, global and per-agent admission limits, deadlines and ambiguous-effect policy, task-result validation, cancellation UX, and reconciliation decisions. Durable’s terminal statuses are not Kaeno’s proposed `outcome_unknown` status (`docs/spec.md:1604-1656`; `src/harness/scheduler.ts:752-883`).
- **Keep contact/application coordination.** Durable serializes Session mutations and queues inputs to a busy conversation, but does not supply Kaeno’s user-priority/bounded-completion-batch policy, result-card acknowledgment, or a guarantee that a contact model narrates a completion. Example 23’s parent report is an ordinary follow-up input; if it is queued when parent abort withdraws queued inputs, that notification can be lost as a model turn even though the child answer remains queryable (`test/examples/23-subagent-background.ts:111-130`; `docs/spec.md:2261-2280`). Keep `directory.ts`, a reduced `contact.ts`, and a verified Durable-focused `execution.ts`; retain application completion state if Kaeno requires inspectable, redeliverable notices independent of narration.
- Keep external-effect safeguards and workspace isolation as application policy. Agent selections store **names**, not code; changed registries, environment, or `cwd` can affect later phases and recovered tool calls (`docs/spec.md:2942-2973`; `test/harness-tools-recovery.test.ts:165-211`). Background ownership and tool allowlists are neither capacity controls nor security sandboxes.

## Non-Obvious Things and Open Questions

- Example 23 deliberately declares its management tool **unsafe** because replaying `stop` could stop newer work (`test/examples/23-subagent-background.ts:156-164`). Its reporter’s stable task-derived request IDs protect the two *submission admissions* across reporter replay; they do not prove exactly-once child computation, notification consumption, or external effects (`test/examples/23-subagent-background.ts:83-130`).
- A completed tool result may be committed while its task is `completing`; terminal receipt and generation continuation wait for ordinary owned work to drain (`docs/spec.md:2111-2141`; `src/harness/tool.ts:378-410`). Treat “result entry exists” and “owner finished” as different events.
- Verify against the pinned build and failure-injection tests whether Kaeno needs an application completion inbox whose outcome and pending notice share the *worker’s* final commit. Decide what to do when a queued parent follow-up is withdrawn, when a notice was admitted but not narrated, and when a model request is resent before its response committed. Also choose and test the host’s single-owner mechanism and required power-loss durability setting. None of those guarantees follows from example 23 alone.
