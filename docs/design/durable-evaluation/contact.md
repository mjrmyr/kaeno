## Components Found

At the supplied commit, **`@earendil-works/pi-durable` is experimental**; its README says the API may change without notice (`packages/durable/README.md:1-3`). Its `Harness` is not the ordinary coding-agent SDK session: it combines conversations, submissions, tasks, entries, and documents on **one Session mutation line**, with atomic commits across those records (`docs/spec.md:45-77`, `src/harness/harness.ts:157-200`).

The relevant built-ins are:

- `Conversation.submit()` and `Submission.status()`, `.wait()`, `.abort()`, plus `Harness.submission(id)` for reacquisition after reopen (`src/harness/harness.ts:87-90,222-224`; `src/harness/submissions.ts:43-92`).
- Per-conversation `pi.inbox` for queued inputs and passive writes, and `pi.live.run` for the current run and its placed submission IDs (`src/harness/inbox.ts:8-27`; `src/harness/live.ts:45-68`).
- Durable `pi.generation` and `pi.tool` tasks, rather than a host callback that must serialize concurrent `prompt()` calls (`src/harness/generation.ts:115-117,664-674`; `src/harness/tool.ts:37-43`).
- `Conversation.viewState()`, `.watch()`, and experimental `watchEvents()` for committed observations—not a delivery ledger (`src/harness/view.ts:89-114`; `src/harness/events.ts:55-88,140-182`).

## Flow and Guarantees

1. **Intake and deduplication.** `submit({type:"input", content, requestId, whenBusy}, context)` returns after admission, **not** after an answer. `Submission.wait()` returns a terminal `done` answer-entry ID or `unanswered` reason; cancelling the wait does not cancel work. A queued submission can instead be withdrawn with `.abort()` (`docs/spec.md:898-913`; `src/harness/submissions.ts:54-92`). A repeated `requestId` is looked up **within that conversation before the busy check or any write**. The same ID and type returns the old submission—even if the new content or `whenBusy` differs; only a change between `input` and `write` is rejected. It is **not** Kaeno’s proposed origin-plus-request-hash comparison (`src/harness/submissions.ts:130-146`; `test/harness-submissions.test.ts:88-119`; compare `docs/design/minimal-kaeno.md:115-117,173-175`). A different conversation may reuse the ID. Provider tool-call IDs are not Session-unique and should not themselves be submission request IDs (`docs/spec.md:2992-2998`).

2. **A busy contact.** An idle input with an empty inbox places `pi.user` and creates a generation in its admission commit. While `pi.live.run` exists, inputs queue: default `followUp`, explicit `steer`, or `whenBusy:"reject"` throwing `ConversationBusy` without a record. Writes queue while busy but append entries **without starting generation** when placed (`src/harness/submissions.ts:141-197`; `docs/spec.md:2208-2235`). A steer joins the *existing* run at a **post-tool-round** boundary, not an arbitrary moment during an in-flight provider request. A follow-up starts a successor run at a successful **final** boundary. Each boundary places **all writes first**, then selected users in submission-ID order; default queue settings choose one steer/follow-up of each eligible mode, or `"all"` can choose all. Neither setting implements Kaeno’s user-over-completion priority or bounded fairness (`src/harness/inbox.ts:50-110`; `src/harness/generation.ts:597-652`; `docs/spec.md:2244-2304`). Tests inspect queued writes preceding users, steer-after-tools, and one versus all follow-ups (`test/harness-inbox.test.ts:94-161,207-238,627-658`).

3. **Failures matter for notification.** A failed or aborted run settles its *placed* inputs `unanswered` but leaves other queued items untouched. They may remain queued while the contact is idle until another submission triggers a boundary. `Conversation.abort()` withdraws queued inputs—including completion notices sent as inputs—but retains queued passive writes. A `write` alone cannot request model narration; a follow-up input can, but even its `done` means the model answered, not that a user saw or understood the notice (`docs/spec.md:2288-2304`; `src/harness/inbox.ts:117-132`; `test/harness-inbox.test.ts:431-456,664-683`; `test/harness-ownership.test.ts:247-263`).

4. **Background completion delivery is possible without a second generic inbox.** The normative spec describes a background reporter task: it submits to a child with a task-derived request ID, waits for settlement, then submits the report to the parent as `whenBusy:"followUp"` with another task-derived request ID. Reexecution of either submission recovers the existing record (`docs/spec.md:3039-3069`). The product *example* implements that pattern, including a task checkpoint containing the report, child-answer deduplication, and reporter-ID-derived parent request ID (`test/examples/23-subagent-background.ts:46-123`). This is **example code, not a tested Kaeno notification contract**: it explicitly notes that a parent abort can withdraw a queued report (`test/examples/23-subagent-background.ts:106-118`). For task results that must remain inspectable or be re-notified under that policy, retain an application result/receipt record and a reconciliation rule in a Durable task or document. Do not infer exactly-once model consumption from submission deduplication.

5. **Availability.** A background task is an ownership boundary: parent ordinary abort and idle traversal do not reach its child conversation or reporter; explicit background abort can. The child runs in its own conversation, while the contact’s current run can answer independently (`docs/spec.md:1956-1979,3039-3067`; `test/harness-ownership.test.ts:188-199`). Contact `submit()` can admit or reject a second request while its model is busy; it cannot promise an immediate second answer during a stalled provider call. Queue admission is not bounded by a built-in Kaeno-specific intake limit (`src/harness/submissions.ts:130-197`; `docs/spec.md:2208-2257`). Reopening requires a persistent backend and scheduling via `resume()` or a progress-seeking call; reads and watches alone do not start recovered tasks (`docs/spec.md:638-651`; `src/harness/scheduler.ts:239-273`).

6. **Live observation is convergent, not reliable notification.** `viewState()` mounts the active transcript and five built-in documents; application documents require their own observation. `watch()` captures a committed snapshot and then exact commit frames, delivering callbacks serially, but after **100 pending frames** replaces the undelivered suffix with a whole-state replacement. Reconnect starts at current state, without replay. `watchEvents()` is experimental, covers **one conversation, not its owned subtree**, and likewise replaces overfull event batches with a snapshot. Neither stream proves that a notification was delivered to a client; use submission/task records for outcomes and an application acknowledgment if required (`docs/spec.md:3981-4035,4036-4085,4087-4093,4217-4230`; `src/session/observation.ts:129-235`; `test/session-watches.test.ts:83-188`; `test/harness-events.test.ts:247-264`).

## Kaeno Boundary Decisions

**Can be removed or folded into Durable:** the proposed separate durable user-input inbox, host-side contact-session serialization of model turns, generic task checkpoint runner, second transcript/task database, and generic completion queue *if* completion is represented by an application reporter task plus durable result state and parent submissions. Durable admits submissions and stores conversation/task/document changes together, eliminating the cross-store gap assumed when using ordinary Pi session files (`docs/design/minimal-kaeno.md:156-169`; `docs/spec.md:45-77,2178-2235`; `src/harness/harness.ts:320-331`).

**Still Kaeno policy:** stable client and delegation identities; reject changed arguments for a reused delegation origin; specialist catalog and configuration snapshots; work/queue limits and deadlines; prioritization and anti-starvation between user turns and completion notices; output/narration rate limits; terminal-result validation and inspectable task cards; whether a withdrawn or failed notification should be reattempted; client acknowledgments; and effect-specific idempotency. The built-in inbox offers ordering and queue modes, **not** those policies (`docs/design/minimal-kaeno.md:55-60,171-183`; `docs/spec.md:2233-2257`). A *logical* contact policy owner remains useful, but a separate contact actor as the only low-level transcript writer is not required to prevent overlapping Durable generations. A separately persisted completion inbox is not automatically required; whether a result document plus reporter suffices depends on Kaeno’s desired re-notification guarantee.

All these guarantees are **scoped to one Durable storage Session**. `requestId` uniqueness is per conversation, not global; an application must first find the same child conversation after a crash. The package assumes one process owns storage and supplies **no cross-process locking** (`README.md:536-549`; `docs/spec.md:652-660`). Moreover, SQLite’s submission lookup is backed by a **non-unique** `(conversation_id, request_id)` index: the normal API’s serialized lookup provides the deduplication, not a standalone SQL uniqueness constraint for arbitrary writers (`src/storage/sqlite/migrations.ts:51-60`; `src/storage/sqlite/storage.ts:497-509`). SQLite’s documented `synchronous=NORMAL` covers process crashes but may lose newest commits on power/host failure (`README.md:536-545`). External effects and user receipt are outside the Session transaction.

## Non-Obvious Things and Open Questions

- A previously queued report submitted under a stable ID remains the **same `unanswered/aborted` submission** if the parent withdraws it; retrying that ID does not redeliver it. Define explicit new-attempt identity or a separate notification state machine if Kaeno requires later delivery (`src/harness/submissions.ts:130-140`; `test/examples/23-subagent-background.ts:106-118`).
- `"steer"` is not interruption of an active model request; it waits for a post-tools boundary, and a no-tools answer can go straight to final selection (`src/harness/generation.ts:513-541,597-652`). Decide whether completions should instead always be follow-ups.
- The example’s report is **model input**, not a passive result card. Decide whether Kaeno should render independently queryable task results immediately and only sometimes spend a contact turn narrating them (`docs/spec.md:4221-4230`; `docs/design/minimal-kaeno.md:181-183`).
- Decide how to enforce bounded intake and completion fairness without losing committed results, and what happens to notices after run failure, parent abort, or a permanently stalled contact provider. No inspected built-in API supplies that policy.
- Pin and regression-test this experimental commit before deleting fallbacks; especially test restarted reporters, identical IDs with changed arguments, queued-report withdrawal, failed-run stranded inbox items, and event-stream overflow.
