## Components Found

**Scope and stability.** I inspected the assigned checkout at `/tmp/kaeno-pi-source`; I did not independently verify its Git HEAD. Its `packages/durable/package.json:2` reports version `1.1.0`, but the README explicitly calls the API **experimental** and says it may change without notice (`packages/durable/README.md:1-3`). Pin the source commit and dependencies for an integration, not just the package name.

- `createRegistry()`, `defineExtension()`, and `Harness.open()` provide a process-owned registry of named tools, sections, hooks, wrappers, and task definitions. The registry starts with built-in generation, tool, and compaction *tasks*, not installed coding tools (`packages/durable/src/harness/registry.ts:9-10,34-52,115-118`; `test/harness-registry.test.ts:121-131`).
- A conversation’s `pi.agent` stores model, thinking level, extension **names**, tool **names**, instructions, and `cwd`; it does not store extension code. `Conversation.configure()` changes choices, and `Conversation.agent()` resolves them against the *current* registry and settings (`packages/durable/src/harness/agent.ts:37-45,82-116,158-239`; `docs/spec.md:708-771`).
- `HarnessOptions.env` supplies an `ExecutionEnv` at each use. The shipped `NodeExecutionEnv` is a local filesystem/process environment, not a sandbox (`packages/durable/src/harness/harness.ts:225-231`; `src/env/node.ts:604-616,803-809`; `docs/spec.md:2921-2928`).
- Persistent backends include Node SQLite and JSONL; memory is nonpersistent. Node SQLite sets WAL and `synchronous = NORMAL` (`packages/durable/README.md:536-545`; `src/storage/sqlite/node.ts:177-209`). Storage has **no cross-process ownership lock** (`README.md:545`).

## Flow

A host can parse a trusted Kaeno directory entry, resolve its requested tool names to installed tool objects, and create a worker conversation with `createConversation({ ownership, agent: { model, thinkingLevel, extensions, tools, instructions, cwd } })`. `agent.extensions` and `agent.tools` passed to creation are objects whose **names** are stored; an array selects exactly those names in order. If omitted, extensions default to all installed ones (or `settings.extensions`), and tools default to every selected extension’s tools. Missing selected names are silently skipped; an absent model fails generation with `no_model` (`packages/durable/docs/spec.md:560-607,737-779,2495-2515`; `src/harness/agent.ts:158-239`). Thus the JSON directory is **not** itself a registry or a built-in specialist selector. Kaeno still needs a small, strict loader/validator and selection/admission policy, but need not invent a second agent execution engine.

At request preparation, the resolved model, thinking level, offered tools, prompt sections and stream options are fixed for that request. Sections render through the selected extensions; instructions render last. A subsequent change is expressed as positional `pi.system` transcript deltas. A call already emitted by the model resolves its tool implementation later, when the tool task runs; changing the selection between these points can yield `tool_unavailable` (`packages/durable/docs/spec.md:854-867,2495-2558,3127-3253`; `src/harness/generation.ts:122-185`; `src/harness/tool.ts:54-61`). A later extension’s same-name tool wins **in its existing position**; selected wrappers then decorate it (`src/harness/agent.ts:161-183`; `test/harness-registry.test.ts:192-233`).

## Boundaries

**A Kaeno definition is not a Durable snapshot.** On reload, `registry.install(newExtensionWithSameName)` replaces the extension in place; an active tool execution keeps its acquired implementation, but later task phases, requests and calls can use new code. Restart reinstalls code afresh and stored names bind to whatever is then installed. Uninstall does not invalidate the stored names: they can become effective again later (`packages/durable/docs/spec.md:3254-3291`; `src/harness/registry.ts:68-94`; `test/examples/31-reload-and-restart.ts:1-3,69-107`). A task definition is instead resolved by task kind and version at reservation: missing, too-old, or failed-to-migrate definitions leave work **live and blocked**, including idle waits; aborting blocked work can produce `orphaned`, not a successful cancellation (`docs/spec.md:1995-2051`; `src/harness/scheduler.ts:826-887`; `test/harness-tasks-recovery.test.ts:428-550`). Versioned task migration does not pin an agent’s prompt, tool implementation, or workspace.

Tool recovery is narrower than “resume the same code”: `pi.tool` records final arguments and replay policy before execution. After interruption it reruns `execute()` only when **both** the stored policy and the currently resolved implementation say `replay: "safe"`; otherwise it returns an `interrupted` error result with retained output. The default is unsafe. A safe rerun rebuilds the environment from the conversation’s **current** `cwd`, not the first attempt’s directory (`packages/durable/src/harness/tool.ts:35-40,83-110,257-261`; `docs/spec.md:2751-2770,2949-2958`; `test/harness-tools-recovery.test.ts:136-211`). Kaeno’s proposed `AgentSnapshot` requires a separate immutable effective-configuration record, compatibility checks, and a policy to block drift; `pi.agent` alone does not provide those guarantees (`docs/design/minimal-kaeno.md:94-101,219-225`).

**Workspaces and capabilities.** `NodeExecutionEnv` gives every local instance the same filesystem identity, `"node:local"`; changing `cwd` changes relative-path resolution, not filesystem permissions or isolation (`packages/durable/src/env/node.ts:72-87,604-616`; `src/env/index.ts:153-178`). The sandbox example records a directory in an application document and returns an environment per conversation; it explicitly says a hosted product would need an environment that actually runs inside a container (`test/examples/29-sandbox-per-conversation.ts:1-4,16-21,39-65`). The reviewer example creates its checkout *in host code* and permits only `read`; it does not implement worktree creation or enforcement for Kaeno (`test/examples/28-reviewer.ts:1-3,41-42,67-90`). `ExecutionEnv` is trusted, not a confinement boundary (`docs/spec.md:2918-2928`).

The shipped `CodingTools` contains **`read`, `write`, `edit`, `bash` only**, and is not automatically installed (`packages/durable/src/tools/index.ts:1-25`). I found no built-in `grep`, `find`, `ls`, skills loader, or MCP integration in the inspected Durable source. The example’s `Skills` is an illustrative extension section, not a shipped discovery facility (`docs/spec.md:2450-2479`). Kaeno’s sample `["read","grep","find","ls"]` therefore cannot be mapped unchanged; implement and explicitly install/select the missing tools, or change the profile (`docs/design/minimal-kaeno.md:207-225`). A prompt saying “read only” is not a substitute for excluding write-capable tools and extensions.

## Non-Obvious Things

- `root(context, { agent, init })` applies these only when it *creates* the root. On reopen it returns the existing root and ignores new choices; configuration updates require `configure()` (`packages/durable/src/harness/harness.ts:306-318,335-352`; `test/harness-conversations.test.ts:73-108`). A task-owned new conversation copies its owner’s stored agent **once**; a fork uses the parent’s as-of agent. Neither copies a fully resolved registry/settings snapshot (`docs/spec.md:677-705`).
- A default extension selection changes when settings or installed extensions change. An explicit array can accidentally omit a permissions/guard extension; there is no registry-wide guard. Unknown tools/models/resources must therefore be rejected by **Kaeno validation** if the design requires errors rather than Durable’s skip/error-at-use behavior (`docs/spec.md:2495-2509,4696-4718`; Kaeno `docs/design/minimal-kaeno.md:219-225`).
- A registry snapshot is an immutable *process view*, not persisted code. Releasing an old extension’s resources immediately after uninstall can break still-running calls. A non-cooperative handler can also keep `close()` pending and storage open (`docs/spec.md:2442-2448,3254-3291,4724-4731`).
- SQLite’s WAL/NORMAL setting is documented for process-crash durability, **not** assured survival of the newest commit after power/host failure. JSONL’s default lacks that latter guarantee too; `fsync: true` has the more qualified marker protocol in `docs/spec.md:4544-4594`. The app must prevent a second live owner independently (`README.md:536-545`).

## Open Questions / Kaeno Decision

Kaeno can delete or greatly reduce the proposed **`execution.ts` session/runtime adapter** and any fallback **`store.ts` that duplicates Durable tasks, submissions, checkpoints, or conversation state**: use Durable conversations, task definitions/documents, and one persistent backend instead (`docs/design/minimal-kaeno.md:60-76`; `packages/durable/README.md:78-124,504-526`). It cannot simply delete `directory.ts` or all of `tasks.ts`: trusted JSON loading, strict tool/model/resource validation, immutable effective-definition pinning and drift handling, specialist selection, global/per-agent concurrency, queue/deadline/token budgets, workspace provisioning/isolation, and single-owner enforcement remain **application policies** (`docs/design/minimal-kaeno.md:171-180,207-227`). The inspected `HarnessSettings` offers request retry/timeout, tool-round execution mode, compaction and inbox modes—not those Kaeno-wide resource quotas (`packages/durable/docs/spec.md:315-395`; `src/harness/scheduler.ts:770-813`).

Before claiming a direct directory-to-agent mapping, decide where to persist each admitted task’s effective agent/tool/resource revision, how to reject an unsupported historical revision on reopen, which explicit read/search tools to ship, and what actual container/worktree capability—if any—enforces workspace boundaries. These are gaps in the direct mapping, not reasons to build a parallel Durable runtime.
