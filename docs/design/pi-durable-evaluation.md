# Pi Durable evaluation for Kaeno

> Package evaluation of the now-current **single-Harness** job design. The [local pi-tui/contact prototype and intended native jobs](minimal-kaeno.md) use the same-process boundary. [Native verification](native-arena/verification.md) covers job primitives, not implemented delegation. The later [host/pod arena](host-arena/synthesis.md) was withdrawn when those requirements were dropped. Original no-tests-run statements describe the earlier evaluation pass.

## Overview

**Verdict: use Pi Durable as Kaeno’s execution and persistence core, but not as Kaeno’s delegation product.** At pinned commit `6fb2e7815167e6b19006fc526d1a5d0f5f998787`, package version 1.1.0, Durable supplies the atomic conversation/task/document substrate that `docs/design/minimal-kaeno.md` could only hypothesize. It does **not** supply Kaeno’s specialist directory, resource limits, result-card policy, reliable completion notification, or safeguards for ambiguous external effects. Its API is explicitly [experimental](https://github.com/earendil-works/pi/blob/6fb2e7815167e6b19006fc526d1a5d0f5f998787/packages/durable/README.md#L1-L3).

Adopt the Durable `Harness` directly with persistent storage and `pi-ai` models. This is a **separate runtime** from the ordinary Pi coding-agent `AgentSession`/`SessionManager`; do not wrap those sessions around Durable or retain their session files as Kaeno’s second source of truth. Durable’s [quick start and runtime model](https://github.com/earendil-works/pi/blob/6fb2e7815167e6b19006fc526d1a5d0f5f998787/packages/durable/README.md#L39-L100) already encompass model turns, tool calls, transcripts, tasks, and application documents.

## Key Concepts

The useful primitive is **one Session commit line**. A commit can update conversation entries, typed application documents, and task records atomically; SQLite writes that batch in one SQL transaction. It cannot include an external API call, model request, user-visible receipt, or a later Session commit. An uncertain storage failure requires reopening rather than assuming a write took effect. [Session guarantees](https://github.com/earendil-works/pi/blob/6fb2e7815167e6b19006fc526d1a5d0f5f998787/packages/durable/docs/spec.md#L65-L77), [SQLite commit](https://github.com/earendil-works/pi/blob/6fb2e7815167e6b19006fc526d1a5d0f5f998787/packages/durable/src/storage/sqlite/storage.ts#L172-L202).

A **submission** is durable admission, not model delivery or user receipt. Idle input starts a run; busy input is queued as a `followUp` or `steer`, or rejected with `whenBusy: "reject"`. Steers enter at a post-tool boundary; follow-ups start a successor run at a successful final boundary. Passive writes do not start generation. The boundary places queued writes first, then selected inputs by ID; one-at-a-time versus all is not Kaeno’s fairness policy. [Admission](https://github.com/earendil-works/pi/blob/6fb2e7815167e6b19006fc526d1a5d0f5f998787/packages/durable/src/harness/submissions.ts#L129-L197), [placement](https://github.com/earendil-works/pi/blob/6fb2e7815167e6b19006fc526d1a5d0f5f998787/packages/durable/src/harness/inbox.ts#L50-L110).

A **task** has an owner, durable input/checkpoint, and terminal receipt. Background ownership is a traversal boundary: ordinary parent abort and idle waits skip background work; explicitly crossing the boundary can abort it. A decided result can remain `completing` until ordinary owned work drains, so “result recorded” and “owner terminal” need not coincide. On open, surviving `running` work returns to `pending` without immediate dispatch; `resume()` or a progress-seeking call enables scheduling. Missing or incompatible definitions block recovery, and an aborted blocked task can become `orphaned`. [Recovery](https://github.com/earendil-works/pi/blob/6fb2e7815167e6b19006fc526d1a5d0f5f998787/packages/durable/src/harness/scheduler.ts#L239-L274), [resolution](https://github.com/earendil-works/pi/blob/6fb2e7815167e6b19006fc526d1a5d0f5f998787/packages/durable/src/harness/scheduler.ts#L803-L883), [states](https://github.com/earendil-works/pi/blob/6fb2e7815167e6b19006fc526d1a5d0f5f998787/packages/durable/src/types.ts#L486-L524).

## How It Works

Build the smallest Kaeno-native path around those primitives:

1. Acquire Kaeno’s **process-lifetime single-owner guard** before opening storage. Open one pinned Durable Harness and persistent backend with explicitly selected extensions and task definitions, reopen the root contact conversation, reconcile application result notices, then `resume()`. `root({agent})` applies choices only on creation; reopening requires an intentional `configure()` for changes. [Root behavior](https://github.com/earendil-works/pi/blob/6fb2e7815167e6b19006fc526d1a5d0f5f998787/packages/durable/src/harness/harness.ts#L306-L352).
2. Admit client input with a stable per-contact `requestId`; return its submission ID immediately. Record or validate Kaeno’s stronger client request identity where required. A duplicate ID of the same type returns the old submission **even if content or busy mode changed**; changing submission type alone errors. [Lookup](https://github.com/earendil-works/pi/blob/6fb2e7815167e6b19006fc526d1a5d0f5f998787/packages/durable/src/harness/submissions.ts#L129-L146).
3. Give the contact an application `delegate` tool that validates a trusted directory entry, capacity, objective, and effective read-only configuration. In **one** `api.commit()`, create-or-find a worker by `api.taskId`, persist its request hash/configuration revision and result reference, create its task-owned conversation if needed, and create a background reporter. Check the current document **inside that commit**; repeat of the same durable tool task and arguments returns the existing task, changed arguments fail. The provider’s `callId` remains useful diagnostic origin data, not this create-once key. The example demonstrates the mapping/creation transaction, but its own product policy is not Kaeno’s. [Example transaction](https://github.com/earendil-works/pi/blob/6fb2e7815167e6b19006fc526d1a5d0f5f998787/packages/durable/test/examples/23-subagent-background.ts#L201-L234), [tool identifiers](https://github.com/earendil-works/pi/blob/6fb2e7815167e6b19006fc526d1a5d0f5f998787/packages/durable/src/harness/tool.ts#L175-L195).
4. Return a short receipt without awaiting specialist inference. Durable commits the tool-result entry, slot and tool outcome **later**, separately from Kaeno’s creation commit. Generation waits for tool tasks to settle before its next turn, but need not wait for the background worker. [Tool settlement](https://github.com/earendil-works/pi/blob/6fb2e7815167e6b19006fc526d1a5d0f5f998787/packages/durable/src/harness/tool.ts#L378-L410), [generation continuation](https://github.com/earendil-works/pi/blob/6fb2e7815167e6b19006fc526d1a5d0f5f998787/packages/durable/src/harness/generation.ts#L595-L646).
5. Let a Kaeno worker task validate its deliverable and atomically commit its terminal outcome, inspectable result document, and pending-notice state. A separate background reporter submits a bounded parent `followUp` under a stable, task-derived request ID. The [example reporter](https://github.com/earendil-works/pi/blob/6fb2e7815167e6b19006fc526d1a5d0f5f998787/packages/durable/test/examples/23-subagent-background.ts#L83-L133) illustrates submissions and checkpoints—not an atomic outcome-to-model-delivery guarantee. Do not substitute `tx.createSubmission()`: it creates a raw record without inbox/admission rules. [Transaction API](https://github.com/earendil-works/pi/blob/6fb2e7815167e6b19006fc526d1a5d0f5f998787/packages/durable/src/session/transaction.ts#L428-L440).

Keep the first release **read-only** and small. A replay-safe *delegate-creation-only* tool is plausible **after verification**: store the keyed mapping and created task in one commit, then on a new invocation inspect the committed mapping/task snapshot and return the existing receipt. Never take the example’s combined `spawn`/`send`/`stop` management tool, flip it to `safe`, and assume stop or messaging is harmless to replay. Its [declared unsafe policy](https://github.com/earendil-works/pi/blob/6fb2e7815167e6b19006fc526d1a5d0f5f998787/packages/durable/test/examples/23-subagent-background.ts#L153-L164) is deliberate.

## Where Things Live

A reduced **proposed**, not yet implemented, Kaeno map is:

```text
src/kaeno.ts       host facade; startup, owner guard, send/inspect/cancel, transport
src/directory.ts   trusted definitions; strict validation and effective revisions
src/contact.ts     contact tool definitions and small admission/fairness policy
src/tasks.ts       delegation identity, quotas, result validation, reconciliation
src/execution.ts   thin Durable setup: registry, models, env, task definitions
kaeno/agents/*.json
.kaeno/state.sqlite    one Durable storage, not a second task database
```

Delete the old design’s **fallback `store.ts` ledger**, separate Pi session files, generic checkpoint runner, and contact actor whose purpose is merely to serialize `prompt()` calls. Reuse Durable’s submissions, task receipts, ownership, atomic documents, scheduler and transcripts. Keep a *logical* contact coordinator for priority, bounded notification/narration, and client UX; keep `tasks.ts` for Kaeno policy rather than low-level task execution. An application result/notice document is **not** a parallel durability engine: it describes Kaeno’s independently queryable delegation outcome and optional acknowledgment atop Durable records. Keep persistent result/notice state in a conversation- or session-scoped document (or retained task outcome), not only in a task-scoped document: task documents retire when their task becomes terminal.

`directory.ts` must explicitly resolve model, thinking level, instructions, tools, extension/resource versions and permitted environment into an effective revision recorded with each task. Stored `pi.agent` contains selections, not frozen implementations: defaults select all installed extensions and their tools, missing selected names can be skipped, and reinstalling an extension under its name changes later resolution. Task-definition versioning does not pin prompts or tool code. [Selection](https://github.com/earendil-works/pi/blob/6fb2e7815167e6b19006fc526d1a5d0f5f998787/packages/durable/src/harness/agent.ts#L158-L239), [registry replacement](https://github.com/earendil-works/pi/blob/6fb2e7815167e6b19006fc526d1a5d0f5f998787/packages/durable/src/harness/registry.ts#L65-L94). Explicitly install only approved capabilities; supply `grep`/`find`/`ls` yourself or change the sample profile. Skills and MCP discovery are not provided by the inspected Durable tool set. A `cwd` and tool filter do not confine host filesystem access.

## Gotchas

**Replay is effect-specific.** Durable’s pattern is commit intent → perform effect → commit outcome. Built-in tools default to `replay: "unsafe"`: after committed intent, recovery reports `interrupted` instead of rerunning. Rerun requires **both** stored and currently resolved policies to be `safe`, and even then an external effect needs its own idempotency key or reconciliation. Model requests may also be resent after interruption. [Effect contract](https://github.com/earendil-works/pi/blob/6fb2e7815167e6b19006fc526d1a5d0f5f998787/packages/durable/docs/spec.md#L1872-L1887), [tool recovery](https://github.com/earendil-works/pi/blob/6fb2e7815167e6b19006fc526d1a5d0f5f998787/packages/durable/src/harness/tool.ts#L58-L117). Kaeno’s `outcome_unknown` is **application metadata/policy**, not a native terminal enum; native outcomes are `completed`, `failed`, `aborted`, `orphaned`, or `faulted`. Do not label an ambiguous remote mutation successfully cancelled. [Outcome types](https://github.com/earendil-works/pi/blob/6fb2e7815167e6b19006fc526d1a5d0f5f998787/packages/durable/src/types.ts#L449-L483).

**Completion submission is not reliable notification.** Parent abort withdraws queued input notices; a reporter retry with the **same** `requestId` finds that existing `unanswered/aborted` submission and does **not** redeliver it. A failed run leaves other queued inputs stranded until another admission triggers a boundary. Define notice attempts and reconciliation separately from the stable completion ID; preserve result cards regardless of narration. [Withdrawal](https://github.com/earendil-works/pi/blob/6fb2e7815167e6b19006fc526d1a5d0f5f998787/packages/durable/src/harness/inbox.ts#L117-L132), [failure boundary](https://github.com/earendil-works/pi/blob/6fb2e7815167e6b19006fc526d1a5d0f5f998787/packages/durable/docs/spec.md#L2288-L2304), [reporter warning](https://github.com/earendil-works/pi/blob/6fb2e7815167e6b19006fc526d1a5d0f5f998787/packages/durable/test/examples/23-subagent-background.ts#L106-L118). `viewState()`, `watch()` and `watchEvents()` observe committed snapshots/changes; watches can replace backlogged frames with a snapshot. They are not client delivery receipts or a replayable acknowledgment ledger. [Watch overflow](https://github.com/earendil-works/pi/blob/6fb2e7815167e6b19006fc526d1a5d0f5f998787/packages/durable/src/session/observation.ts#L190-L235), [event scope](https://github.com/earendil-works/pi/blob/6fb2e7815167e6b19006fc526d1a5d0f5f998787/packages/durable/src/harness/events.ts#L140-L182).

**Operational guarantees need explicit limits.** Node SQLite uses WAL with `synchronous = NORMAL`: process-crash recovery is not a promise that the newest commit survives power/host failure. Transaction locking is not a cross-process Harness lease. Abort and `close()` signal active invocations—including background ones—but cannot force a non-cooperative effect to stop; close can remain pending while joining it. [SQLite configuration](https://github.com/earendil-works/pi/blob/6fb2e7815167e6b19006fc526d1a5d0f5f998787/packages/durable/src/storage/sqlite/node.ts#L177-L194), [storage warning](https://github.com/earendil-works/pi/blob/6fb2e7815167e6b19006fc526d1a5d0f5f998787/packages/durable/README.md#L536-L545), [close path](https://github.com/earendil-works/pi/blob/6fb2e7815167e6b19006fc526d1a5d0f5f998787/packages/durable/src/harness/scheduler.ts#L731-L745).

**Validation still required; no tests were run for this evaluation.** Before calling Kaeno durable, run pinned-build fault-injection experiments at creation/tool-result and worker-outcome/report boundaries; replay the same task ID with changed arguments; abort queued reports and attempt redelivery; fail a contact run with queued inputs; remove or change an agent definition mid-task; exercise quotas, stalled effects, shutdown, second-owner rejection, watch overflow, and the chosen power-loss requirement. These are acceptance experiments, **not** guarantees established by the inspected examples or tests.
