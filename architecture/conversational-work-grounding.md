# Grounding: conversational Kaeno

User wants a short immediate plan/acknowledgement, then chat free for another request while work runs. Completion should cause a later natural Kaeno reply. This turn is design/discussion only: no runtime implementation, deployment, Git operations, cluster changes or tmux. Existing provider/model/chat preferences must stay; workers remain disposable and assigned-only skills stay frozen. Public-only runtime source retrieval unrelated; do not recover deleted docs or inspect Git history.

## Traced existing flow / why it has this shape
src/telegram.ts polls allowlisted messages, atomically advances offset + creates background Turn task owned by conversation. /stop conversation.abort default scope, /new conversation.reset. Turns are background delivery wrappers, NOT background delegated work. thread uses one ownerless durable conversation per telegram/pi/schedule key.
src/threads.ts Turn submits input with stable requestId + whenBusy followUp, awaits submission, checkpoints notify text, sends Telegram then terminal. sendMessage + checkpoint cannot be atomic, so duplicates are possible after external send succeeds then process crashes. No proactive route on thread records (just conversationId, createdAt). configureThread refuses refresh for run/inbox/ANY pending/running/waiting conversation task, so new background work would wrongly pin frontdesk refresh if unchanged.
src/agents.ts delegate replay-safe execute creates/reuses child owned by current delegate TOOL TASK; persists AgentState.skills, execution image, cache claim and env token; creates sandbox (409 tolerated), awaits readiness, submits worker with delegate:toolTaskId, waits worker completion, returns answer/usage, finally deletes pod except when shutting down. Parent remains busy until call/owned child finishes. This ownership elegantly ties cancellation, synchronous result and disposable cleanup together. Background redesign must preserve those protections, not just drop await.
AgentState is conversation-scoped doc, template string + frozen binding + sandbox locator. agentChange sets model/instructions/allowed tools/delegates. describe(template) includes assigned skill metadata. delegate authorization and templates currently resolve via CURRENT config, not immutable job-level config. Sandbox child configuration frozen when created; existing children replay original binding even current catalogue empty. Root template/skills refresh on idle admission. Root and worker model settings separate, do not change them.
sweeper removes pods whose annotation kaeno.io/task names missing or terminal task; CURRENT annotation is delegate tool id. Never relabel job ownership without changing cleanup consistently. Remote-env exposes workspace/binaries; no main cache/SQLite mount in worker. emptyDir task files survive container restarts, not pod deletion.
src/api.ts POST turn submits directly (not Turn task), watchEvents trace includes reasoning/tool calls/children, waits that one submission then closes stream. Abort default conversation scope. GET threads only lists IDs. No persistent event/job feed. A job completion after done has nowhere to push in this protocol.
pi-extension/kaeno/index.ts model provider performs one HTTP request for latest user text, reads trace until done, returns one AssistantMessage then closes. Cannot spontaneously display a later answer just by extending server submit logic: needs separate durable feed + extension event lifecycle/UI integration, or honest MVP status/reconnect retrieval. No pi API inventions.
src/schedule.ts cron task captures notify route on Turn input, accepts missed slots skipped; creation deduplicated in same commit as slot marker. Job completion must retain schedule-specific notify; routing by global 'last chat' is wrong, multiple callers may share a thread.
src/kaeno.ts resolves skill refs first, constructs agents/Turn registry, Harness open(SQLite), refresh roots/resume, starts API/Telegram/schedules/sweeper. SIGTERM shutdown agents first then Harness.close, active work preserved. Job definitions must registered before resume.
homelab quota6 pods TOTAL, includes main -> at most5 sandboxes, quota may include other future/debug pods. Need admission/queuing, not promise unbounded concurrent workers. Resource limits10Gi/10CPU namespace; main limits1Gi/1CPU and each worker2Gi/2CPU, so the ACTUAL unchanged quota supports at most4 workers (the fifth would request11Gi/11CPU total), despite the pod-count ceiling allowing5. Admission must use all resource ceilings, not assume5. /stop and /new semantics need product decision. New completion vs user turn can race; same-conversation turns serialized via inbox.

## Framework evidence
Installed pi-durable1.1.0 README ownership: parent idle waits descendants; background:true task is an ownership boundary skipped by parent idle and normal abort; abort({background:true}) crosses. Tx creates tasks/conversations in same commit. Task IDs, background flags, checkpoints/status and task graph already durable. Don't mirror all task status into a hand-synced jobs DB if derive suffices.
/tmp/pdex/23-subagent-background.ts (read-only downloaded upstream example) has background Anchor owning child and separate Reporter delivering/submitting result with dedup request IDs. Its persistent subagents are NOT user requirement; adapt relevant semantics only. ToolExecutionApi operations are invocation-bound, reject after invocation ends: cannot keep api/context in detached Promise. Durable tasks use their own runtime/context. Root background task may directly own one disposable child; terminal anchor approach not necessarily needed.
node_modules/@earendil-works/pi-durable/dist/harness/types.d.ts Submission.whenBusy steer/followUp/reject; conversation submit wait; abort background option; Tx scanTasks; task definition phases/abort. Native completion input currently ordinary user-input content: clarify internal envelope/source identity and prevent worker result granting credentials/authority or impersonating user command.

## Open product constraints to make concrete
Response order if a job finishes before acknowledgement delivered (especially Telegram separately checkpointed sends); background results when frontend idle/busy; durable completion routing and retention; /new detach/cancel/context epoch; status/steer/cancel per job vs wholechat abort; fanout joins/multi-step work under root chats; capacity without unnecessary scheduler framework; legacy active synchronous tasks across deployment (don't silently strand them); external Telegram exactly-once impossible without idempotent send API; pi eventual feed when disconnected. Don't claim verified runtime design yet.

## Candidate shapes to compare
A: frontdesk Kaeno launches worker background jobs directly; worker results reenter root for reviews/follow-on work. Job task owns worker lifecycle, root short turns coordinate multiple jobs and joins.
B: frontdesk Kaeno launches a per-request WORK conversation (same chosen orchestrator template/model, scoped role); work orchestrator retains blocking delegation to disposable workers and multi-step review, while chat stays free. Background Work task owns work conversation + its foreground delegate subtree. Work result reenters chat; channel delivery separate from execution.
These must be truly compared on simplicity of lifecycle/joins/context/delivery, not just preserving old code.
