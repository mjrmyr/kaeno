Sandbox One pod per sandboxed delegation, running envd, which is pi-durable's NodeExecutionEnv behind HTTP and passes the env conformance suite. Kaeno's env hook routes the child's tools there. The pod has public internet access (HTTPS, git over SSH with a deploy key), and nothing internal is reachable: no cluster, LAN or tailnet. It holds no other credentials and is deleted when the delegation ends.
Channels The pi extension (pi:<session> threads) and a Telegram bot using long polling and an allow-list. Telegram turns are durable tasks that survive restarts.

Core idea

1 · YOUSend a task to kaeno over the tailnet (browser, CLI or curl).
2 · REASONKaeno, a Pi Durable agent, splits the task into self-contained briefs.
3 · DELEGATEEach brief becomes one Kubernetes Job, which runs one pod with its own empty workspace.
4 · MONITORKaeno watches the Job status and reads each pod's stdout (JSON lines).
5 · CONCLUDEKaeno combines the sub-agent results into one report.
6 · REPORTThe report is saved on the PVC and shown to you in the UI/API.

Kubernetes is the runtime

The design has no custom operator, no message queue and no worker pool. A sub-agent is a Job, so Kubernetes does the scheduling, restarts, deadlines, cleanup and status reporting. Kaeno only creates, watches and deletes Jobs.

The pod is the sandbox

Each sub-agent pod gets its own emptyDir workspace and a read-only root filesystem. It has no ServiceAccount token and no shared volumes. Network access is denied except DNS and the LLM. A sub-agent cannot see kaeno's files or another sub-agent's files.

Sub-agents can't reach kaeno

Sub-agents write their progress and result to stdout. Kaeno reads that through the Kubernetes pods/log API. This means no network path from sub-agent to kaeno, no callback endpoint, and no credentials inside the sandbox.

Interface specifications

I1 — Task API HTTP/1.1 · JSON · Tailscale · Bearer

The Service kaeno has the annotations tailscale.com/expose: "true" and tailscale.com/hostname: homelab-kaeno, following the same pattern as homelab-llm. It has no Ingress and no Cloudflare route. The tailnet ACL lets only your user reach tag:k8s:8080. The bearer token from the SOPS Secret is a second check, because anyone who reaches this endpoint can start compute.

Endpoint Request Response Notes
GET / — HTML UI The existing public/client.html, adapted.
POST /api/tasks {requestId, text} 202 {id, status:"running"} Idempotent on requestId. Starts a new Pi Durable root conversation for the task.
GET /api/tasks — [{id, text, status, createdAt}] Newest first.
GET /api/tasks/:id — {id, text, status, subagents:[{id, brief, phase, summary?}], report?} subagents is read live from the Jobs labelled kaeno.io/task=:id. Kaeno doesn't keep its own copy.
POST /api/tasks/:id/cancel — 202 Deletes the task's Jobs using the label selector, then marks the task cancelled.

I9 — Orchestrator tools Pi tool calls

Tool Effect → result
spawn_subagent
{brief ≤ 8 KB, deadlineMin ≤ 60} 		Builds the Job from the fixed template, named sa-<task8>-<hash(toolCallId)>. It then calls POST /apis/batch/v1/…/jobs. A 409 AlreadyExists counts as success, so a replay after a crash is safe. Returns {id}. If 3 sub-agents are already running or the task has used 6, it returns an error and the model has to wait.
wait_subagents
{ids, timeoutSec ≤ 600} 		Watches the Jobs until any of them finishes or the timeout passes. Returns [{id, phase, progress: last 5 lines, result?, reason?}]. Polling this is how kaeno monitors.
cancel_subagent
{id} 		DELETE job?propagationPolicy=Background. A 404 also counts as success.

The final assistant message of the root conversation is the report. Kaeno saves it to tasks.report and sets status=done.

I2 — Kubernetes API HTTPS · ServiceAccount

The client is plain fetch against https://kubernetes.default.svc, using the projected SA token and NODE_EXTRA_CA_CERTS=/var/run/secrets/kubernetes.io/serviceaccount/ca.crt. It needs no client library: there are only 5 calls. 

apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata: {name: kaeno, namespace: kaeno}
rules:
- apiGroups: [batch]
  resources: [jobs]
  verbs: [create, get, list, watch, delete]
- apiGroups: [""]
  resources: [pods]
  verbs: [get, list, watch]
- apiGroups: [""]
  resources: [pods/log]
  verbs: [get]
# no secrets, no exec, no cluster scope

Calls used: POST jobs · GET jobs?labelSelector=kaeno.io/task=…&watch=1 · GET pods?labelSelector=batch.kubernetes.io/job-name=… · GET pods/{pod}/log?tailLines=… · DELETE jobs/{name}.

I4 — Result channel stdout JSON Lines · exit code 

# zero or more, any time
{"type":"progress","text":"wrote parser, running tests"}
# exactly one, last line
{"type":"result","status":"succeeded",
 "summary":"≤ 500 chars for the report",
 "output":"≤ 32 KB full answer"}
Job condition Exit Kaeno sees
Complete 0 succeeded + parsed result
Failed / BackoffLimitExceeded ≠0 failed + last progress lines
Failed / DeadlineExceeded killed timed_out
Complete but no result line 0 failed "no result"
Job missing (TTL or deleted) — lost

Sub-agents run Pi with storage/memory, so there is no durable store inside the sandbox. If a pod dies, its work is gone, and kaeno decides whether to spawn a fresh one.

I5 — LLM HTTP · OpenAI chat completions

Both roles use pi-ai's openai-completions API against MODEL_BASE_URL, over cluster DNS (not the tailnet). contextWindow must stay equal to --ctx-size 32768. Kaeno can optionally be pointed at a hosted provider with KAENO_MODEL=provider/id plus a key from the Secret. Sub-agents always use the local model.

The kaeno Role can create pods in this namespace, and Pod Security "restricted" stops it from creating privileged or hostPath pods. The k3s API server sits behind the 10.43.0.1:443 ClusterIP and is DNAT'ed to <node-ip>:6443. The egress rule has to match the address after DNAT, so check this once on the cluster.

Task sequence — from your task to the report

State & recovery — who owns what

State Owner (single source of truth) Lifetime
Task record and report kaeno SQLite tasks table (PVC) forever
Orchestrator reasoning Pi Durable conversation (same SQLite file) forever
Sub-agent status Job conditions (API server) until TTL (24 h)
Sub-agent progress and result Pod log (kubelet) until TTL (24 h)
Sub-agent files emptyDir in the pod until the pod exits

Kaeno never copies sub-agent status into its own database, so the two can't drift apart. The only thing it stores is the final report.

What happens when …

  • kaeno restarts (deploy, OOM, node reboot): sub-agent Jobs keep running, because they don't depend on kaeno. When the Deployment comes back, Pi Durable resumes each running task's conversation from the PVC. Any tool call that gets replayed is safe: spawn has a deterministic name and treats 409 as success, wait is read-only, and cancel treats 404 as success.
  • a sub-agent crashes or hangs: the Job fails with backoffLimit: 0, or activeDeadlineSeconds kills it. Kaeno sees this through wait_subagents and the model decides whether to re-spawn with a better brief.
  • you retry a POST: the same requestId returns the same task.
  • kaeno is down for more than 24 h while Jobs finish: the Jobs and logs are gone, and kaeno reports them as lost. Raise the TTL if this matters to you.
  • the quota is full: kaeno's own cap of 3 running sub-agents is what normally applies. The ResourceQuota is a hard backstop in case of a bug.

Decisions and the alternatives I rejected

Question Chosen Rejected Why
How is a sub-agent run? One Job per brief A long-lived worker pool pulling from a queue · a custom CRD + operator · kubernetes-sigs/agent-sandbox A pool shares one filesystem across tasks, which breaks the isolation requirement. A CRD or operator adds a controller to write and run, and Jobs already do that job. agent-sandbox is worth revisiting if you need warm pools or gVisor.
How do results come back? stdout JSON lines via pods/log Sub-agent POSTs back to kaeno · shared PVC · termination message A callback would need a network path and a credential inside the sandbox. A shared PVC breaks filesystem isolation. A termination message is capped at 4 KB.
How does kaeno talk to Kubernetes? fetch + SA token, 5 calls @kubernetes/client-node · shelling out to kubectl Five REST calls don't justify a large dependency or a kubectl binary in the image.
Where does kaeno live? The same kaeno namespace as its sub-agents A separate namespace for the orchestrator You asked for one shared namespace, and a namespace-scoped Role is enough. Labels plus NetworkPolicy separate kaeno from the sub-agents.
How do you reach it? Tailscale Service + token Cloudflare tunnel / traefik Ingress · a chat bot This reuses the existing homelab-llm pattern. Anything that can start compute should never be public. A chat bot could be added later as a second I1 client.
Who retries a failed sub-agent? The orchestrator model Kubernetes backoffLimit > 0 Running a failed brief again unchanged usually fails again. Retrying is a reasoning decision, and Kubernetes retries would also hide the failure from kaeno.
Sub-agent durability? None (in-memory Pi) pi-durable inside each pod A pod's work is disposable by design, and the brief is the unit of retry. That removes a store from every sandbox.

Risks & open questions

The model is the bottleneck

Qwen3-4B Q4 on CPU with one slot has to plan, call tools, monitor and write the report, and it is shared with every sub-agent. Expect calls to queue up and planning to be weak. Splitting the slot (--parallel 2 = 16 K context each) collides with Pi's 16 K compaction reserve. Recommendation: start with a hosted model for kaeno only (the optional egress rule) and keep the sub-agents local, or accept that this setup runs tasks slowly and one call at a time.

Containers share the host kernel

The sandbox stops filesystem and network access, but it is not a VM. That's enough for code the agent writes itself. If sub-agents will run untrusted third-party code, add a gVisor or Kata RuntimeClass later: it's one field in the Job template.

Sub-agents have no internet

By default they can't git clone, npm install or browse the web. That is the safest default, but it limits what they can do. You need to decide whether some briefs get an egress allowlist (for example, a second kaeno.io/egress: internet label with its own policy).

Inputs and outputs are text only

Sub-agents start with an empty workspace and return at most 32 KB of text. Handing over files, or returning artifacts such as a git branch or patch, is out of scope for this simple version. A git remote is the natural next step.

Bootstrap prerequisites

  • Your homelab README says you lost the kubeconfig. Get it back from /etc/rancher/k3s/k3s.yaml on the node (or use sudo k3s kubectl) before rolling this out.
  • The GHCR image has to be public, or you need an imagePullSecret.
  • Check the apiserver-egress NetworkPolicy on k3s/kube-router once (because of the DNAT to :6443).
  • Add tag:k8s:8080 for homelab-kaeno to the tailnet ACL, for your user only.

Deliberately left out

Steering a sub-agent while it runs, nested sub-agents, a chat front-end, push notifications, multiple users, and observability (Grafana is already next on your homelab list). Each of these can be added later without changing the interfaces above.
